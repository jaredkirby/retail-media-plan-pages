03 / Authority

Autonomy belongs to an action and a scope

The same agent can draft a report automatically while a launch, budget amendment, or client release still needs a specific human decision. Promotion applies to proven capabilities and procedures.

    What a usable grant must specify
    • Action class, authorized role, client, account, retailer, and native entity scope.
    • Exact or conditional preconditions, financial and rate limits, protected entities, and expiry.
    • Required source coverage, current-state check, provider preview, and effect verification.
    • Revocation, escalation, unknown-outcome resolution, and procedure version.
    • Build, independent QA, launch, financial amendment, optimization, and report release are separate authorities.

      05 / Proof and build order

      Build real vertical slices

      Each slice connects source evidence, useful work, human authority, and verified closure. Tests include interruption and changed inputs. Passing a synthetic demo does not prove a real operating cycle.

      01

      Prove the sources

      One real Shopperations scope and complete Skai MCP evidence, including every expected profile and commitment.

      Exit: accepted source contracts and explicit capability gaps.
      02

      Prove a decision

      Shared-budget finding, external wait, human review, material reopening, and safe retry.

      Exit: one accepted revision with no partial decision state.
      03

      Prove a launch

      Exact build packet, builder receipt, independent QA, correction, launch approval, and go-live check.

      Exit: verified launch with durable handoffs.
      04

      Prove an effect

      Supported Skai preview, specific approval, application, lost-response handling, and read-back.

      Exit: known effect state and later outcome assessment.
      05

      Prove closeout

      Operational closure, mature measurement, financial reconciliation, report release, and scoped learning.

      Exit: separate closure evidence for each clock.
      06

      Prove reuse

      Second client and another retailer or tactic; authenticated roles, concurrent reviews, tenant isolation, and restore.

      Exit: configuration reuse with a shared domain model.

      Historical cases to preserve

      H1

      Omitted shared-budget members

      Complete membership, one allocation, visible supersession.

      H2

      Build approved; launch held

      Exact packet, receipt, independent QA, separate launch authority.

      H3

      Unresolved keyword attribution

      Traffic evidence stays useful; unsupported sales claims stay unavailable.

      H4

      MCP schema drift

      Retain failure, repair with replay, require fresh acceptance.

      H5

      Partially eligible planning refresh

      Use valid reports while retaining the blocked dependency.

      Product measure

      Less operator effort to verified closure

      Track edits, evidence requests, missed work, reopened cases, and mature outcomes.

      06 / Evidence and confidence

      Retain what works; prove what is missing

      Current project

      Domain and contract discipline

      Goal buckets, identity, task packs, source limits, review memory, and staged learning. A controlled interruption exposed partial review state across file writes.

      Retail Media

      Transactional recovery mechanics

      Evidence retention, revisions, leases, idempotency, and publication recovery tests. Separate stores and blocked real acceptance remain design gaps.

      Evidence and official references
      • Full rebuild proposal (retained project note), proposed domain model (retained project note), acceptance stories (retained project note), and evidence register (retained project note).
      • Skai Reporting and Campaign Actions: tool families, previews, and current human-approval guidance.
